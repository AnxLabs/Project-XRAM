# Local LAN benchmark: 2026-10-29

**Topology:** the Windows desktop was wired over Ethernet and the Debian laptop was on Wi-Fi. See the [mixed-LAN follow-up](NETWORK-STUDY.md) for link reports, variability, failures and the distinction from wired/RDMA research.

These are fresh measurements on a disposable two-machine LAN setup, using only generated fixtures. They are not results from private documents or an application workload. The sample sizes are small, p95 is an observed sample percentile rather than a reliable tail estimate, and one run cannot establish general performance.

## Test setup

- Client: AMD Ryzen 5 5600X, 6 cores / 12 threads, **48 GiB DDR4-3200 observed** (the requested specification stated 32 GB), Windows 11 Pro build 26300, Python 3.11.9. The scratch file was on a Kingston NVMe SSD.
- Server: Intel Core i5-11400H, 6 cores / 12 threads, approximately 15.7 GiB RAM reported, Debian 13, Linux 6.12.94, Python 3.13.5. The test process had a 48 MiB payload cap, an 8 MiB search cap, eight connection workers, one search worker, three queue slots and a 2 s queue wait.
- Client Ethernet reported 1 Gbps; the server used Wi-Fi. A 12-packet ICMP snapshot had 0% loss, 1–57 ms range and 10 ms mean. Wi-Fi signal was approximately -50 dBm in a separate snapshot; link quality and radio load can change. These are not controlled network conditions.
- The 8 MiB random byte fixture was generated by Python's seeded PRNG; a second repeated-text fixture measured compressibility. A generated 1 MiB, 1,024-row synthetic vector fixture exercised the fixed search. No real documents, model data or private application data were used. Fixture hashes and all individual timing samples are in [raw results](results/lan-2026-10-29.json).

## Results

Ten samples per single-client case. Latency includes Python and SHA-256 where noted; p95 is the nearest-rank observed sample. Throughput is calculated from median time and logical payload size, not wire speed.

| Operation | Median | p95 | Median logical throughput |
| --- | ---: | ---: | ---: |
| TLS ping, new connection | 20.81 ms | 37.02 ms | — |
| Remote 8 MiB read and verify | 179.46 ms | 199.75 ms | 44.58 MiB/s |
| Remote 8 MiB write **including delete** | 153.88 ms | 176.98 ms | 51.99 MiB/s |
| Local RAM copy and verify | 5.61 ms | 6.60 ms | 1,425.72 MiB/s |
| Warm SSD file read and verify | 7.62 ms | 12.13 ms | 1,049.48 MiB/s |
| Local vector score | 13.20 ms | 21.22 ms | — |
| Remote vector search over persistent TLS | 19.64 ms | 78.20 ms | — |

SSD results can be served by the Windows file cache; no cold-storage result was measured. Remote writes include an additional delete request, while reads use a fresh TLS connection and verify SHA-256. These results are not a direct measure of raw network or SSD device bandwidth.

| Compression fixture | Compressed / original size | Compress median / p95 | Decompress median / p95 |
| --- | ---: | ---: | ---: |
| Random bytes | 100.03% | 154.66 / 170.10 ms | 4.45 / 4.55 ms |
| Repeated text | 0.63% | 13.00 / 13.44 ms | 6.04 / 6.33 ms |

Compression was zlib level 1 and does not help incompressible data. These are generated extremes, not a forecast for a user's data.

| Concurrent clients | Completed / attempted | Other results | Completed/s | All-response median / p95 |
| --- | ---: | --- | ---: | ---: |
| 1 | 5/5 | none | 36.67 | 19.39 / 53.19 ms |
| 4 | 20/20 | none | 53.91 | 69.69 / 75.42 ms |
| 8 | 16/40 | 24 queue full | 52.08 | 28.98 / 89.20 ms |

Each client made five sequential requests using its own persistent session; threads share the Windows Python process. Failure responses are included in latency. The eight-client median includes fast rejections and is not a success-latency measure. For four clients, framed application requests totaled 3,840 bytes sent and 4,856 received, excluding TLS and transport overhead. Only one search ran at a time; the test is neither a soak test nor a sustainable-capacity estimate.

The Windows benchmark process showed 22,679,552 bytes working set before fixture creation, 44,494,848 after, and 68,800,512 peak; it held local data and these snapshots do not prove RAM savings. Server RSS was 31,764,480 bytes before seeding, 41,205,760 after 9,437,184 payload bytes, and 49,991,680 afterward, with zero process swap in those snapshots. The server had handled an earlier run, so its initial RSS includes allocator history. Payload limits are not RSS limits.

A separate single outage rehearsal stored a synthetic 64 KiB object, stopped the isolated server, detected `ConnectionRefusedError`, regenerated and SHA-256-verified the fixture locally in 1,086.92 ms, then restarted the server. The old object was absent and republishing/retrieval verified in 167.97 ms. This was a manual recovery experiment, not automatic application fallback. Raw stage records: [seed](results/failure-seed.json), [offline](results/failure-offline.json), [restart](results/failure-recover.json).

## Reproduce

Follow [installation](../docs/INSTALLATION.md), create fresh disposable credentials, start an isolated server with search enabled, `--limit 50331648 --search-limit 8388608 --workers 8 --search-queue 3 --search-wait-ms 2000`, and select an empty temporary scratch directory. Host and certificate names must match your own LAN. Supply the token through a protected file or stdin:

```sh
python benchmarks/local_lan.py --host SERVER_PRIVATE_IP --port PORT --cert /private/cert.pem --token-file /private/token --scratch /temporary/scratch --mib 8 --samples 10 --concurrent-rounds 5
```

The harness creates synthetic objects with unique names and attempts to delete them. If it is interrupted, stop the isolated server or allow expiry. The program emits raw JSON; do not publish it without checking it for environment-specific metadata. The separate `benchmarks/failure_recovery.py` supports `seed`, `offline`, and `recover` phases; stop and restart only the specific disposable server between phases. Never run these tests against a production service. Hardware, network conditions, filesystem cache state, and Python version can change results.
